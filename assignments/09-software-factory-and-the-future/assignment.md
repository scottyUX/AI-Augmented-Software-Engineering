# Week 9 — The Software Factory: One App, Three Stacks

## Overview
When generating a working app takes minutes, the bottleneck moves from *writing* code
to *choosing, comparing, and integrating* it. This week you'll experience the "software
factory": build the **same application in three distinct technology stacks**, with at
least one generated by an **AI app platform ([bolt.new](https://bolt.new/))** and at
least one using a **non-JavaScript** language.

**New domain:** an **Event RSVP / meetup** app (not the reference's developer command
center).

## Learning goals
- Use an AI app-generation platform end-to-end and evaluate its output.
- Compare stacks for the same requirements; see how AI narrows or widens tradeoffs.
- Reflect on self-running, self-improving systems and where SDLC is heading.

---

## Minimum functional scope (the Event RSVP app)
- CRUD a primary resource: **events** (title, date, location, capacity).
- RSVP flow: users can RSVP yes/no; enforce capacity.
- Persistent storage appropriate to the stack.
- Basic validation and error handling.
- A simple but functional UI for the main flows.
- Clear local run instructions (and deploy links if you deploy).

## Stack requirements
Build **three** versions of the RSVP app, each on a **distinct** stack. Examples:
- MERN (MongoDB, Express, React, Node)
- Django + React (or Vue)
- Flask + vanilla JS
- Next.js + Node / NestJS
- Ruby on Rails (full-stack)

Constraints:
- **≥1 version must be built with [bolt.new](https://bolt.new/)** (you may explore
  Lovable, Figma Make, etc. for the others).
- **≥1 version must use a non-JS language** on frontend or backend (Python/Django,
  Ruby/Rails, …).

## Tips for AI app generators
- Start from a clean prompt describing the concept, entities, routes, and UI flows.
- Describe data models and relationships explicitly; iterate on CRUD, validation, and
  components.
- Keep each version isolated to avoid dependency conflicts.
- Export/sync generated code and commit it as its own standalone project folder.

## Part — Reflection on the factory
Beyond building, write a short reflection tying this to the lecture:
- What did the AI generator get right/wrong out of the box, and how much manual fixing
  was needed?
- If this app had to **improve itself** (add features, fix bugs) with minimal human
  input, what would break first? What guardrails would you add before trusting that?

## Deliverables
Under `event-rsvp/`, submit **three** project folders (one per version), each with:
- Source code.
- `README.md`: prerequisites, install/setup, run, and env configuration.
- Notes on deviations, known issues, and manual fixes after generation.

Plus a `writeup.md`:
- App concept + which stack each version uses.
- Three app descriptions (one per version).
- The factory reflection above.

## Evaluation (100 pts)
- 10 — Concept meets the minimum functional scope.
- 10 — Three genuinely distinct stacks.
- 10 — bolt.new used for at least one version.
- 10 — Non-JS language used in at least one version.
- 20 **each** (×3 = 60) — per version: source in `event-rsvp/` (5), complete README (5),
  working functionality (5), version description in `writeup.md` (5).
